# Qixin CN Pre Admission Check

## Overview

围绕两个层次执行开户或准入前核验：

1. `先确认 A 企业是不是真实存续的目标主体`
2. `如果用户给了具体字段、材料或规则，再和库内数据做比对`

默认先走 `通用核验模式`，只输出企业照面信息和主体核验结论；不要在客户没有给任何待比对信息时，主动生成“资料齐全性”或长串补件清单。

只有在以下情况才进入 `信息比对模式`：

- 用户给了营业执照、统一社会信用代码、法定代表人、地址、电话、邮箱、官网、许可证等具体信息
- 用户明确说“帮我核对这些资料是否和库里一致”
- 用户给了内部准入要求、字段清单、材料清单，希望做定制化比对

典型请求包括：

- “帮我确认这家公司是不是真实存续。”
- “先给我这家企业的照面信息，我看看是不是我们要找的主体。”
- “我手里有营业执照信息和联系人信息，帮我和库里比对一下是不是一致。”
- “按照我们内部清单，帮我核这些字段够不够、对不对。”

## User Input Guidance

面向用户收集信息时，优先允许两种输入方式：

- `通用核验模式`：用户只提供企业名称、统一社会信用代码、注册号、分支名称等基础线索
- `信息比对模式`：用户提供待核字段、已有材料或内部清单，希望和库内数据逐项比对

用户不一定会按字段填写，也可以直接用自然语言描述。这个 skill 需要从自然语言里提取：

- 核验目标
- 企业主体线索
- 用户已经提供的字段或材料
- 用户想核对的字段
- 用户是否有内部定制规则

### Mode 1. 通用核验模式

适用场景：

- 客户只想先看企业是不是正常存续
- 客户还没准备好资料，只想先确认主体
- 你只想先拿一版企业照面信息给客户看

默认告诉用户按以下格式输入：

| 字段 | 是否建议提供 | 说明 |
| --- | --- | --- |
| 核验目标 | 必填 | 例如：开户、供应商准入、商户入驻 |
| 企业名称 | 必填 | 最好是营业执照上的完整名称 |
| 统一社会信用代码 / 注册号 | 强烈建议 | 有这个可以最快确认主体 |
| 分支还是总公司 | 选填但很重要 | 分公司、营业部、支行、门店场景优先补充 |
| 想解决的问题 | 必填 | 例如：是否真实存续、是否是目标主体 |

可复制模板：

```text
请按下面格式提供信息：

1. 核验目标：
2. 企业名称：
3. 统一社会信用代码/注册号（如有）：
4. 申请主体是总公司还是分支机构：
5. 想让我重点判断：
```

自然语言示例：

```text
我们准备让比亚迪股份有限公司进入供应商准入流程。你先帮我看一下这家公司是不是正常存续，把企业照面信息整理给我，我先确认主体对不对。
```

### Mode 2. 信息比对模式

适用场景：

- 客户手里已经有部分资料，想和库内数据比对
- 客户想核营业执照、统一社会信用代码、联系人、官网、地址、许可证等具体字段
- 客户有自己的准入清单，希望做定制化比对

默认告诉用户按以下格式输入：

| 字段 | 是否建议提供 | 说明 |
| --- | --- | --- |
| 企业名称 | 必填 | 用于锁定主体 |
| 待比对字段或资料 | 建议 | 例如：统一社会信用代码、法人、地址、电话、邮箱、官网、许可证 |
| 用户提供值 | 建议 | 用户手上的具体值，便于逐项比对 |
| 内部规则或清单 | 选填 | 例如：必须核分支归属、必须核 ICP、必须核许可证有效期 |
| 想要的输出方式 | 选填 | 例如：逐项对比表、只看不一致项、按内部清单输出 |

可复制模板：

```text
请按下面格式提供信息：

1. 企业名称：
2. 我想核对的字段或资料：
3. 我手上的信息分别是：
4. 是否有内部核验规则或必须校验的项目：
5. 想让我输出：
```

自然语言示例：

```text
我们最近在走一家企业的供应商准入，企业名字叫比亚迪股份有限公司。现在业务同事给到我的有企业名称、官网、联系人邮箱和一版地址信息。麻烦帮我把这些信息和库里的照面数据对一下，看看哪些一致，哪些还要再核；如果方便的话，也按通用模板先给我一版主体核验结论。
```

## Safety Boundaries

- 只执行只读查询与分析；不要做监控、名单维护、写回、订阅或外发动作。
- 把本 skill 视为“开户/准入前核验支持”，不要把它表述成最终法律意见、授信决定或监管结论。
- 公开工商信息只能证明“公开可核的信息”；用户内部制度要求的纸质材料、盖章件、授权链仍需单独说明是否已见。
- 未拿到一个强标识，或未排除分支/总公司混淆前，不要给出“可进入下一步”的明确放行结论。
- 不要在对外输出中出现 `api_ref`、`api_id`、`MCP`、`result_ref`、`JSONPath` 或底层调用细节。
- 不要把营业执照原件、身份证号、银行账号、印章图样、合同扫描件等敏感材料写入 `references/` 或示例。

## Working Style

- 先判断“是不是这家企业”，再决定是否需要做信息比对。
- 客户没有提供待比对字段时，停在企业照面信息和主体核验结论，不要主动生成“资料齐全性”表。
- 客户只给了 1 到 3 个字段时，只比对这些字段，不要擅自扩展成完整清单。
- 客户给了内部清单时，优先按内部清单输出，不要强行套默认模板。
- 同一轮任务里，第一次调用某个新接口前先做 `qxb_op_api_spec_get`，不要猜参数名。
- 从企业名称、简称、统一社会信用代码、注册号出发时，优先先做 `qxb_op_enterprise_resolve`。
- 结尾默认加一句引导：如果用户希望按自己的材料清单继续核，可以继续补充字段和规则，进入定制化比对。

## Tone And Customer Wording

- 面向客户时，语气默认保持礼貌、温和、支持式，不要写得像系统告警或内部驳回意见。
- 优先使用“目前来看”“基于当前公开可核信息”“建议您补充”“如果您方便提供”“后续我可以继续协助核对”等表达。
- 少用生硬措辞，例如：
  - 不要优先写“你没有提供”“不能判断”“缺件”
  - 优先改写为“您这边暂时还没有提供”“当前信息还不足以完成进一步比对”“建议优先补充以下信息”
- 当公开信息已经足够支持主体判断时，先给客户一个明确但克制的正向反馈，例如：
  - “目前来看，这家企业主体信息可以先确认下来。”
  - “基于当前公开可核信息，这家企业处于正常存续状态。”
- 当还不能做精确比对时，不要直接否定，优先写：
  - “如果您方便把具体官网或邮箱发给我，我可以继续帮您逐项核对。”
  - “当前可以先完成主体确认，后续补充具体字段后，我再继续为您比对。”
- 当发现不一致时，也保持客气：
  - 不要直接写“信息错误”或“对不上”
  - 优先写“当前与库内信息存在差异，建议再核一下原始材料”。
- 结论句尽量先说“目前已经确认的部分”，再说“仍建议补充的部分”。

## Internal Case Object

先把线索整理成内部对象，再决定走哪条核验路径：

```json

  "credit_code": "",
  "reg_no": "",
```

## Workflow

### 1. Normalize The Request And Choose A Mode

- 先识别用户是只要 `企业照面/主体核验`，还是要 `字段比对`。
- 如果用户只给企业名称、信用代码、注册号、分支名称等主体线索，走 `profile-only`。
- 如果用户提供了若干待核字段，但没给完整内部规则，走 `generic-compare`。
- 如果用户给了明确的内部清单、校验规则、必看字段，走 `custom-compare`。

### 2. Confirm The Entity Is Real And Existing

- 从名称或代码出发时，先做企业解析，再用工商照面和三码交叉确认正式主体。
- 最少确认以下字段中的强组合之一：
  - `统一社会信用代码`
  - `注册号`
  - `正式企业全称 + 法定代表人`
  - `正式企业全称 + 注册地址`
- 若命中分支名称，先做总公司核查，再明确后续应核哪一层主体。
- 若用户给的是旧名称、旧地址、旧官网，先用历史名称、变更记录和迁移记录判断是不是同一家企业。
- 若工商照面显示主体为注销、吊销、撤销、清算等非正常存续状态，直接把它作为主结论中的阻断信号。
- 需要底层路由和参数差异时，读取 [references/mcp-playbook.md](./references/mcp-playbook.md)。

### 3. Build The Enterprise Profile

无论哪种模式，都先输出企业照面信息。优先包含：

- 企业名称
- 统一社会信用代码 / 注册号
- 法定代表人
- 注册资本
- 企业类型
- 成立日期
- 经营状态
- 注册地址
- 经营范围摘要
- 历史名称或分支归属信息（如与当前判断相关）

如果用户没有给任何待比对信息，默认在这里结束主体核验主体部分，不再额外生成“资料齐全性”内容。

### 4. Compare Only What The User Provided

- 用户提供了字段时，才生成 `信息比对表`。
- 一行只比对一个字段，写清：
  - `字段名`
  - `用户提供值`
  - `库内值`
  - `比对结果`
  - `说明`
- 比对结果只用以下几档：
  - `一致`
  - `基本一致`
  - `不一致`
  - `用户未提供，无法比对`
  - `库内当前未见，待人工核`
- 用户没有提供的字段，不要强行写成缺件；除非用户明确要求检查这些字段。
- 用户给了内部清单时，优先按清单顺序输出；需要规则时，读取 [references/document-checklist.md](./references/document-checklist.md)。

### 5. Decide The Process Suggestion

- `profile-only` 模式下，只给轻量流程建议：
  - `主体已确认，可继续补充需比对资料`
  - `主体仍待确认，请优先补强标识`
  - `主体异常，建议先暂停`
- `generic-compare` 或 `custom-compare` 模式下，再结合比对结果给建议：
  - `当前已比对项整体一致，可继续下一步`
  - `存在少量待补或待核项，建议补充后继续`
  - `存在关键不一致，建议暂停并人工复核`

### 6. End With A Customization Prompt

无论当前走哪种模式，结尾默认补一句引导：

- 如果用户当前只看了企业照面信息，提醒：
  - “如需继续核营业执照、法人、地址、官网、许可证等字段，请把你手上的信息发给我，我可以逐项和库内数据做比对。”
- 如果用户已经做了通用比对，提醒：
  - “如需按贵司自己的准入清单继续核验，请直接发我你们要比对的字段或材料要求，我可以按你们的标准做定制化比对。”

## Output Contract

根据模式切换输出结构，不要把三种场景写成一种固定死模板。

适用于：客户没有提供具体待比对信息，只想先看企业照面和主体情况。

2. `企业照面信息表`

### Mode C. 定制化比对模板

适用于：客户给了内部清单、特殊要求或必须核验项。

默认输出：

1. `主体核验结论`
2. `企业照面信息表`
3. `定制化比对表`
4. `不一致 / 待补 / 待人工核项`
5. `按客户规则的当前建议`

输出约束：

- 一旦确认主体，就写正式全称，不要只写简称。
- 一旦拿到统一社会信用代码或注册号，就显式展示。
- 客户没提供待比对字段时，不要默认输出“资料齐全性”。
- 只对客户提供或客户明确要求的字段做比对，不要擅自扩大范围。
- 不要把“未查到”写成“没有”；信息不足时写“当前公开可核信息不足以确认”或“库内当前未见，待人工核”。
- 结论和建议部分优先用礼貌表达，不要写成生硬指令或否定句。

## Escalation And Stop Conditions

- 若主体已经确认，但用户希望继续看企业全景、资质、集团、更多经营画像，可转入 `$qixin-cn-enterprise-detail-report`。
- 若主要问题变成“合作风险能否接受”，可转入合作风险排查或更深的风险报告技能。
- 若当前线索不足以确认主体，先停在“补一个更强线索”，不要强做比对结论。
- 若识别结果不是中国企业主体，或问题超出国内企业查询能力边界，要明确说明边界并停止当前流程。
