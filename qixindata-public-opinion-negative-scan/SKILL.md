# 企业负面舆情与新闻扫描

## 概述

将本 skill 视为“面向合作前、品牌、公关和商务判断的轻量负面舆情扫描”，而不是全网监测平台、司法经营风险体检或完整尽调报告。

本 skill 只回答三件事：

- 目标企业在最近窗口内出现了多少个负面舆情事件
- 这些负面舆情的质量如何
- MCP 与联网结果里哪些是同一事件、哪些只是转载、哪些证据不足

本 skill 明确不做以下事情：

- 不调用 `cn_cooperation_risk_scan`
- 不输出“低、中、高”之类的舆情风险评级
- 不把文章数量直接等同于事件数量
- 不把未经甄别的自媒体内容直接写成确定事实

## 适用范围

优先用于以下需求：

- “帮我看一下 A 企业最近有没有明显负面舆情”
- “近 90 天这家公司有多少负面新闻，质量怎么样”
- “合作前扫一下最近新闻和舆情，给出处”
- “区分一下这是多个负面事件，还是同一事件被重复报道”

如果用户要的是司法、处罚、执行、异常经营、税务、供应链、关联方、主体尽调等内容，这不是本 skill 的重点，应改用更合适的风险类 skill。

## 默认参数

除非用户明确指定，否则默认使用以下口径：

- 扫描窗口：最近 `90` 天
- 重点观察：最近 `30` 天
- 扫描对象：单个已确认主体的中国企业
- 计数方式：按“事件”计数，不按“文章篇数”计数

## 硬性规则

1. 先确认企业主体，再查新闻与舆情。若企业名称存在明显歧义、候选主体不唯一或与用户提供信息冲突，先停止并要求确认，不继续给结论。
2. 只使用新闻与舆情相关能力，不主动扩展到合作风险、处罚、执行、经营异常等聚合风险接口。
3. `QXBMCP` 与联网结果必须做交叉去重，不能把同一事件在两个来源中各记一次。
4. 结论只能写“数量”和“质量”，不能私自上升为风险评级。
5. 不能因为文章很多就直接判定问题严重；必须先完成事件归并、来源甄别和严重性判断。
6. 对事实不清、仅有标题、原文不可回溯、来源明显薄弱的内容，要明确写成“争议性内容”或“证据不足”，不能写成确定事实。
7. 对重复转载、洗稿、站群聚合、同源分发内容，原则上只作为传播密度参考，不增加事件数量。
8. 输出中每个关键判断都要能回指到具体出处，至少包含日期、标题、来源和链接或可追溯线索。

## 最小工作流

### 第 1 步：确认主体

先调用 `qxb_op_enterprise_resolve`。

执行原则：

- 使用解析结果中的规范企业全称
- 如能拿到统一社会信用代码，一并记录
- 若存在多个合理候选且无法唯一确认，停止并提示主体待确认

### 第 2 步：获取 MCP 新闻底稿

优先使用以下接口：

- `cn_company_news`
- `cn_company_news_detail`

执行建议：

- 首次调用前，如参数口径不确定，先用 `qxb_op_api_spec_get`
- 默认查询最近 `90` 天
- 优先筛选与负面相关的情感属性、舆情标签、事件分类
- 对疑似重要负面项，再用 `cn_company_news_detail` 取正文、来源、原文链接和更完整的上下文

目标不是把所有新闻全量抄出，而是提取“疑似负面事件候选集”。

### 第 3 步：联网补充搜索

在 `QXBMCP` 新闻结果之外，使用联网搜索补充最近窗口内的公开报道。

推荐检索思路：

- `<企业全称> 负面`
- `<企业全称> 争议`
- `<企业全称> 投诉`
- `<企业全称> 维权`
- `<企业全称> 质量`
- `<企业全称> 事故`
- `<企业全称> 通报`
- `<企业全称> 舆情`

需要时追加时间词与限定词，例如：

- `<企业全称> 2026 投诉`
- `<企业全称> 最近 90 天 争议`
- `<企业全称> site:gov.cn 通报`

联网结果的目标是补齐 `QXBMCP` 未覆盖或覆盖不完整的负面事件，不是重复搬运已经在 `QXBMCP` 中完整出现的同一报道。

### 第 4 步：事件级去重与归并

必须按“事件”而不是“文章”归并。优先依据以下要素判断是否为同一事件：

- 事件主题是否一致
- 涉及主体是否一致
- 时间是否接近
- 核心事实是否一致
- 是否存在共同原始来源或共同公告依据

默认归并规则：

- 同一事件的多篇报道，记为 `1` 个负面事件
- 同一媒体的转载、转发、搬运，记为 `1` 个来源链
- 多家媒体对同一事件独立报道，不增加事件数，但可提升传播密度判断
- 同一主题但时间、事实或处理结果明显不同，可拆分为不同事件

### 第 5 步：负面质量判断

不要给评级，只从以下维度描述“质量”：

- 来源级别：权威机构、主流媒体、行业媒体、自媒体、论坛/社媒
- 事件严重性：一般投诉、集中维权、监管通报、重大事故、经营争议、品牌争议
- 证据完整性：仅标题、可见摘要、可见正文、可追溯原文或公告
- 时间新鲜度：近 `7` 天、近 `30` 天、近 `90` 天
- 传播密度：单篇、少量多源、集中传播

推荐写法：

- “近 90 天共识别到 `2` 个负面事件，其中 `1` 个为主流媒体持续报道的消费者投诉争议，`1` 个为单篇自媒体质疑，证据较弱。”
- “负面舆情数量不多，但其中 `1` 个事件来源较权威、原文可回溯，质量高于一般转载型负面。”

避免写法：

- “综合判断为中高风险”
- “新闻很多，所以问题严重”
- “网上有人说，因此可以认定为事实”

## 负面判定口径

默认可纳入负面事件候选的内容包括：

- 明确的消费者投诉、维权、群体争议
- 产品或服务质量争议
- 安全事故、伤害事故、运营事故
- 监管通报、公开点名、行业负面报道
- 品牌争议、重大公关事件、失实争议但已形成传播

默认不纳入负面事件数量的内容包括：

- 单纯的中性公司新闻
- 营销软文、宣传稿、无实质信息的转载
- 与目标企业同名但无法确认属于同一主体的报道
- 只有模糊标题、正文缺失且无法回溯来源的内容

若内容介于两者之间，可保留在“待人工确认”中，但不要计入确定负面事件数。

## 输出要求

固定按以下结构输出，保持简短、可核验、可追溯。

### 1. 扫描范围

- 企业名称
- 主体确认情况
- 扫描窗口
- 数据来源范围：`QXBMCP 新闻` + `联网公开搜索`

### 2. 负面舆情数量概览

至少说明：

- 识别到的负面事件数量
- 相关报道总篇数的大致数量
- 其中近期 `30` 天内的新近事件数量

推荐表述：

- `最近 90 天识别到 3 个负面舆情事件，相关报道约 11 篇；其中最近 30 天新增 1 个事件。`

### 3. 负面舆情质量摘要

用自然语言概括：

- 主要来源层级
- 严重性分布
- 证据强弱
- 是否存在集中传播

### 4. 事件清单

每个事件尽量保持 3 到 5 行，包含：

- 事件编号
- 时间
- 事件标题或主题
- 事件摘要
- 文章数与是否多源传播
- 质量判断
- 主要出处

### 5. 重复与甄别说明

明确写出以下内容：

- 哪些 `MCP` 结果与联网结果已归并为同一事件
- 哪些内容属于转载、洗稿或同源分发
- 哪些内容证据不足，未计入事件数

## 来源要求

1. `QXBMCP` 来源应尽量给出新闻标题、时间、来源、原文链接或 `oid` 对应线索。
2. 联网来源必须写明网站或媒体名称，并附可访问链接。
3. 若同一事件有多个来源，优先保留最原始、最权威、信息最完整的 1 到 3 个出处。
4. 输出中要尽量标明具体日期，不用“最近”“前几天”这类模糊说法代替。

## 执行备注

- 首次调用 `cn_company_news` 或 `cn_company_news_detail` 前，如不确定参数名或过滤条件，先调用 `qxb_op_api_spec_get`，不要猜参数。
- 若 `QXBMCP` 已经提供完整标题、时间、来源和原文链接，联网只用于补充，不重复摘录相同事件。
- 若联网仅检索到低可信度内容，而 `QXBMCP` 无相应印证，应保守表述为“发现争议性内容，但证据不足”。
- 若用户明确指定时间窗、关键词或只看某类负面事件，优先按用户条件收缩范围。
- 输出时要把“事件数量”和“文章数量”严格分开写，避免混淆。
