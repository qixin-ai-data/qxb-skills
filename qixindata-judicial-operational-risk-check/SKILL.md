# 司法与经营风险体检

将本 skill 视为“面向法务与风控的完整体检”，而不是全景尽调或极简红旗扫描。

默认目标：
- 先确认企业主体
- 再完成司法、处罚/合规、经营异常三大模块体检
- 默认输出 `简版 Markdown 报告`
- 只有当用户明确要求 `结构化结果`、`JSON`、`机器可读结果`、`API 入参/出参对接格式` 时，才额外输出 `结构化 JSON 摘要`

不要改造或扩展既有的决策建议字段设计。需要给出合作判断时，沿用既有风险等级与合作建议口径，不新增审核建议字段、不新增补件字段。

## 工作流

### 1. 确认企业主体

先调用 `qxb_op_enterprise_resolve`。

执行原则：
- 仅处理中国大陆企业
- 优先采用解析结果中的规范全称
- 如果存在多个合理候选且无法唯一确认，先停止自动体检并要求用户确认
- 不要猜测 `eid` 或自造主体映射

### 2. 先取总览，再补代表性细节

默认先使用以下最小组合：
- `cn_cooperation_risk_scan` (`55.29`)：司法、处罚、税务、经营异常等风险总览
- `cn_company_composite_risk` (`72.51`)：综合风险评分与等级依据
- `cn_company_justice_risk` (`79.23`)：司法风险强度补充
- `cn_customer_due_diligence` (`47.51`)：主体基础信息、状态、历史沿革、关联关系补充

按需补充，不做默认全量明细拉取：
- `cn_company_risk_statistics` (`27.59`)：当需要风险数量摘要时补充
- `cn_company_credit_score` (`30.4`)：当需要补充企业质量/信用视角时补充

首次调用任何接口前，如参数名不确定，先用 `qxb_op_api_spec_get` 查询规格，不要猜参数。

### 3. 明细接口触发规则

只有在以下情况下才补单项明细接口：
- 聚合结果只给到计数或标签，无法支撑简版报告中的事实摘要
- 某项风险将显著影响最终合作判断，需要代表性细节
- 聚合结果与其他模块结果冲突，需要核验
- 用户明确要求查看诉讼、处罚、经营异常某一类细节

优先补以下明细：

#### 司法风险
- `17.5` 被执行企业
- `19.1` 开庭公告
- `47.4` 立案信息
- `66.1` 限制高消费
- `34.1` 股权冻结
- `7.1` 司法拍卖
- `51.4` 破产案件

#### 处罚与合规风险
- `32.1` 行政处罚
- `51.1` 环保处罚列表
- `56.1` 严重违法
- `66.34` 产品召回
- `79.17` 产品投诉
- `69.75` 外部黑名单
- `66.56` 违法违规建设

#### 经营异常与税务风险
- `1.55` 经营异常
- `20.1` 欠税信息
- `63.2` 非正常户
- `20.3` 重大税收违法
- `25.1` 动产抵押
- `26.1` 股权出质

如果聚合结果已经足以支撑结论，不要重复调用并行明细接口。

### 4. 体检范围与写法要求

默认写以下 5 个模块：
- `企业基本情况`
- `司法风险体检`
- `处罚与合规体检`
- `经营异常与经营风险体检`
- `关联方风险提示`

其中前三个风险模块必须是本 skill 的重心。

每个模块统一按以下顺序写：
1. 模块结论
2. 结果摘要
3. 代表性记录

如果某模块无命中：
- Markdown 里保留一句结论即可
- JSON 里保留稳定键名与空数组

### 4.1 司法记录的稳定判断口径

不要因为“司法案件数量较多”就直接上调结论。先区分案件结构，再判断风险强度。

优先按以下顺序判断：
1. 先看是否命中被执行、失信被执行、限制高消费、司法拍卖、股权冻结、破产等高敏司法风险
2. 再看公司在案件中的身份分布，是以 `原告/申请人` 为主，还是以 `被告/被申请人/被执行人` 为主
3. 最后再看案件类型、时间集中度、金额和是否持续进入执行阶段

当出现以下情形时，默认按“诉讼活跃但风险可控”表述，不把案件数量本身写成负面结论：
- 司法记录较多，但样本中以 `原告`、`申请人`、`维权方` 身份为主
- 案由以知识产权、仿冒、不正当竞争、合同追偿等主动维权类案件为主
- 未见执行类、失信类、限高类、冻结类高敏命中

推荐表述：
- `司法记录存在一定数量，但当前样本以原告/申请人身份的维权案件为主，未见明显执行承压信号，司法风险整体可控。`
- `案件数量不宜单独视为负面因素，需结合身份结构与案件类型综合判断。`

避免表述：
- `诉讼较多，因此司法风险较高`
- `案件数量较多，说明合作风险偏高`
- 在未区分原告/被告结构前，仅凭计数直接上调风险

### 5. 关联方风险边界

关联方风险只做有限穿透，用于提示风险传导，不把它写成目标企业已直接命中同类风险。

优先使用：
- `55.5` 实际控制人
- `55.3` 实际受益人
- `33.9` 疑似关联方
- `59.5` 主要人员对外投资任职
- `47.51` 中的集团、投资、主要人员信息

只保留与目标企业关系最强、且仍为存续/在业/开业状态的核心关联主体。

### 6. 风险等级与合作建议

默认沿用既有评分和建议口径：
- 风险等级优先参考 `72.51`
- 必要时结合 `79.23`、`30.4`、`27.59` 做人工校正
- 合作建议继续沿用既有 `低/中/高风险 -> 合作建议` 映射

详细判断口径读取 [risk-rating-method.md](./references/risk-rating-method.md)。

## 输出要求

输出前先读取 [output-contract.md](./references/output-contract.md)。

默认输出：
1. 简版 Markdown 报告

仅当用户明确要求结构化结果时，再额外输出：
2. 结构化 JSON 摘要

### Markdown 报告要求

- 面向法务、风控、业务评审阅读
- 默认写成“简版体检报告”，不要写成长篇全景报告
- 结论先行，重点突出司法、处罚、经营异常
- 只保留足以支撑判断的代表性事实，不堆砌全量记录
- 正文不要出现接口名、参数名、`api_id`、`api_ref`、`jsonpath`、`result_ref`
- 不要写“根据某接口返回”“调用某接口发现”等过程化表述
- 仅在末尾 `信息来源说明` 章节中，可以简短列出本次实际调用过的 MCP 接口名；保持精简，不展开参数、路径或技术细节

### JSON 摘要要求

- 仅在用户明确要求时输出
- 结构稳定，优先固定键名
- 保留 `source_refs` 与 `data_gaps`
- 风险模块聚焦本次体检主题，不再默认铺开全景模块
- 不要把整段原始接口返回直接嵌入 JSON

## 执行备注

- 聚合优先，细节按需补洞
- 目标是“足以支撑判断的完整体检”，不是“把所有接口都查一遍”
- 对历史记录、轻微记录、孤立记录保持克制表述
- 对重大司法、处罚、经营异常信号要保留时间、机关/法院、结果、金额/标的等关键字段
- 如果某项数据理论上应有但未取到，写入 `data_gaps`
