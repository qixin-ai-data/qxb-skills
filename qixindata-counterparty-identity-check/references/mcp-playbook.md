# MCP Playbook

在需要底层接口路由、参数差异或聚合接口钻取方式时再读取本文。

## Always-On Rules

- 从名称、简称、曾用名、统一社会信用代码或注册号出发时，先做 `qxb_op_enterprise_resolve`。
- 第一次调用某个新接口前，先做 `qxb_op_api_spec_get`。
- 国内企业查询优先传正式企业全称、统一社会信用代码或注册号，不要猜 `eid`。
- 只做查询与分析，不做监控、名单维护或其他写操作。
- 聚合接口返回大结果时，先看 preview，再按需局部钻取。

## Core API Shortlist

- `cn_company_registration_face` (`1.41`, 参数 `keyword`)
作用：确认当前工商照面，优先核正式名称、统一社会信用代码、法定代表人、经营状态、成立日期、经营范围。

- `cn_company_triple_codes` (`79.34`, 参数 `name`)
作用：补齐统一社会信用代码、组织机构代码、注册号；适合做三码交叉确认。

- `cn_company_historical_names` (`24.28`, 参数 `keyword`, `skip`)
作用：确认曾用名；适合处理旧合同主体、历史口径或品牌迁移。

- `cn_company_change_records` (`1.47`, 参数 `keyword`, `skip`, `type_code`)
作用：解释名称、地址、联系方式、负责人、分支变化。常用 `type_code`：
`1` 名称变更
`5` 地址变更
`6` 联系方式变更
`8` 负责人变更
`11` 分支机构变更

- `cn_branch_parent_check` (`79.18`, 参数 `name`)
作用：用分支名称反查总公司；适合识别“实际应签总公司还是分支”。

- `cn_company_branches` (`1.49`, 参数 `keyword`, `skip`)
作用：从总公司向下核分支；适合确认某个分公司是否确实属于目标主体。

- `cn_company_contact_info` (`1.51`, 参数 `keyword`)
作用：核注册地址、联系电话、邮箱等联系方式。

- `cn_company_domains` (`16.1`, 参数 `name`)
作用：核企业备案域名和网站信息；适合用官网线索辅助确认主体。

- `cn_company_annual_report_websites` (`1.53`, 参数 `keyword`, `skip`)
作用：核企业年报网址；适合补充网站、网址类型、启用时间等信号。

- `cn_company_same_phone_entities` (`62.1`, 参数 `phone`)
作用：按电话反查关联企业。注意：仅用于扩展候选，不要单独当成最终确认依据。

- `cn_company_migration` (`79.26`, 参数 `name`, `skip`)
作用：核企业迁移历史；适合处理旧地址、跨区迁址和“这家公司是不是搬过地方”的问题。

- `cn_company_industrial_parks` (`79.31`, 参数 `name`, `skip`)
作用：核企业所属园区；适合把园区线索当作辅助证据。

- `cn_company_development_zones` (`88.24`, 参数 `keyword`, `skip`)
作用：核企业所属开发区；适合把开发区线索当作辅助证据。

- `cn_customer_due_diligence` (`47.51`, 参数 `keyword`, 可选 `dimension`, `is_history`)
作用：在主体仍有歧义，或需要一次性查看基础信息、集团信息、分支、域名等多个板块时作为聚合兜底。建议：先看 preview，再局部钻取，不要默认全量展开。

## Recommended Route By Clue Type

- 统一社会信用代码或注册号：`企业解析 -> 工商照面 -> 三码`

- 完整企业名称：`企业解析 -> 工商照面 -> 按现有线索补一项辅助核验`

- 简称、品牌名、曾用名：`企业解析 -> 历史名称 -> 名称变更记录 -> 必要时聚合尽调`

- 分公司、营业部、支行、门店：
`分支所属总公司核查 -> 明确签约层级 -> 必要时反查总公司分支列表`

- 电话：`同电话企业 -> 候选集合 -> 工商照面/三码进一步确认`

- 官网、备案域名、企业邮箱：
`域名信息 -> 年报网址 -> 联系方式`

- 旧地址或迁址疑问：`工商照面 -> 地址变更记录 -> 迁移情况`

- 园区或开发区：`工商照面 -> 园区/开发区归属`

## Special Route For Likely Contracting Entity

- 当需要输出“根据当前线索推测的签约主体”时，优先走：
`企业解析 -> 工商照面 -> 按冲突点补 1 到 2 个辅助接口`

- 常见补强组合：
`历史名称 + 名称变更记录`
`联系方式 + 域名信息`
`地址变更记录 + 迁移情况`

- 如果领先候选仍不够稳，再用 `cn_customer_due_diligence` 拉聚合视角，但只钻与身份确认相关的区块。

## Special Route For Better Contracting Entity

- 当用户问“是不是还有更合适的签约主体”时，优先走：
`当前主体工商照面 -> 分支所属总公司核查/分支列表 -> 必要时聚合尽调中的集团信息`

- 常见判断场景：
- 当前主体是分支，但用户目标更像总公司签约。
- 当前主体是品牌运营公司，但合同、授权或收款安排更像应落在总公司或另一法人主体。

## Special Route For Name Or Brand Confusion Risk

- 当用户问“会不会山寨”“是不是蹭品牌”“是不是同名误导”时，优先走：
`企业解析 -> 工商照面 -> 历史名称 -> 变更记录 -> 联系方式/域名信息`

- 如需扩大核查，再补：
`客户信息尽调` 中与 `企业基础信息`、`集团信息`、`域名信息`、`分支信息` 相关的板块。

- 重点不是证明“违法”，而是判断：
- 当前主体是否与用户想找的品牌/公司存在明显错位。
- 是否存在多个近似主体，容易误签。
- 官网、邮箱、地址、法定代表人等是否支持当前主体身份。

## Special Route For Candidate Comparison

- 当需要输出“其他可能主体或候选项对比”时，优先走：
`企业解析 -> 工商照面 -> 按冲突点补 1 到 2 个辅助接口 -> 保留 2 到 3 个候选`

- 常见候选对比维度：
- 名称近似度
- 地址是否能对上
- 法定代表人是否一致
- 成立日期或经营状态是否一致
- 是否为分支/总公司关系
- 官网、邮箱、电话是否支持

- 如果只是要做候选项展示，不必把每个候选都做成完整尽调；只要足够说明“为什么像”和“哪里不像”即可。

## Aggregate Query Patterns

只在使用聚合尽调接口时参考：

- `$.data.ent_info`
作用：企业基础档案

- `$.data.group_info`
作用：集团和母子关系摘要

- `$.data.domain_list[0:10]`
作用：域名信息摘要

- `$.data.branches_list[0:10]`
作用：分支机构摘要

## Fallback Strategy

- 基础工商信息已经足够确认时，停止扩查。
- 多个候选依然互相接近时，优先补一个更强线索，而不是继续堆更多弱证据。
- 聚合接口过大时，先用局部区块确认身份，再决定是否继续下钻。

## Source Labels For User-Facing Tables

面向用户输出对照表时，`核验来源` 建议统一使用以下标签：
- `工商照面`
- `三码`
- `历史名称`
- `变更记录`
- `分支所属总公司核查`
- `分支机构`
- `联系方式`
- `域名信息`
- `年报网址`
- `迁移情况`
- `园区归属`
- `开发区归属`
- `客户信息尽调`

这些标签可直接出现在用户可见表格中；不要把 `api_ref`、`api_id` 或其他技术字段直接展示给用户。
