# Qixin CN Counterparty Identity Check

## Overview

围绕“先找对主体，再决定能不能合作”执行中国企业主体核验。
默认输出简洁、可落地的核验结论，而不是完整尽调报告；只有在主体仍有歧义时，才扩大证据面。
如果用户不知道该补什么信息，主动给一个简短的填写提示模板，帮助用户补充更容易消歧的字段，再进入核验。
如果证据还不足以确认唯一主体，也不要停在“我不知道”；应明确写出“根据当前线索推测更可能的签约主体”，并同步提示是否存在更合适的签约主体、是否存在名称/品牌混淆风险，以及还有哪些候选主体值得继续比对。

典型请求包括：
- “帮我确认 A 企业是不是我们要签约的那家公司。”
- “这个简称对应哪家工商主体，会不会重名？”
- “合同里写的是分公司，实际应该跟总公司签吗？”
- “对方给了旧名称、旧地址或官网，帮我确认是不是同一家公司。”
- “你先推测我更应该签哪家公司，再告诉我有没有更合适的主体。”
- “这家公司会不会是山寨的，或者只是蹭品牌名称？”

## Safety Boundaries

- 只执行只读企业查询；不要调用任何监控、订阅、名单管理或写入类能力。
- 把本 skill 视为“合作前主体核验支持”，不要把它表述成最终法律意见。
- 至少拿到一个强标识，或两个互相独立的中等证据，再说“确认匹配”。
- 只有简称、品牌名、行业、城市、园区等弱线索时，不要直接下确认结论；优先补一个更强线索。
- 电话、邮箱、域名、园区、开发区信息只能作为辅助证据，不能压过统一社会信用代码、注册号、分支归属等更强证据。
- 如果目标看起来像分公司、营业部、支行、门店或其他分支口径，先确认用户要签的是该分支还是总公司。
- 对外可以展示“核验来源”这一列，但只用业务可读标签，例如“工商照面”“三码”“历史名称”“分支所属总公司核查”“联系方式”；不要暴露 `api_ref`、`api_id`、`MCP`、`result_ref`、`JSONPath` 或底层调用细节。
- 不要把“山寨”“仿冒”当成已经确认的事实。只能写“名称/品牌混淆风险”“疑似仿冒待进一步核验”这类审慎结论，并说明依据。
- 不要把合同草稿、银行账户、身份证号、印章信息等敏感材料写入 skill 的 `references` 或示例。

## Working Style

- 先小后大。若“工商照面 + 三码 + 一项补充核验”已经足够区分主体，不要默认拉全量尽调。
- 一旦确认了企业全称或统一社会信用代码，后续统一以该正式主体继续核验，不要在多个简称之间来回切换。
- 在同一轮任务里，第一次使用某个新接口前先调用 `qxb_op_api_spec_get`，不要猜参数名。
- 用户从企业名称、简称、曾用名、统一社会信用代码或注册号出发时，优先先做 `qxb_op_enterprise_resolve`。
- 需要底层接口路由、参数差异、推荐组合时，再读 [references/mcp-playbook.md](./references/mcp-playbook.md)。
- 需要处理冲突证据、重名候选、分支/总公司混淆、名称/品牌混淆风险时，再读 [references/evidence-rules.md](./references/evidence-rules.md)。

## Workflow

### 0. Prompt The User When The Input Is Too Thin

- 如果用户只说“帮我查一下这家公司”“确认一下是不是这家”之类，而没有给出足够线索，先给一个简短提示，不要直接长篇追问。
- 优先使用像产品前端一样的短句、轻提示和可复制模板，不要用审计说明书口吻。
- 提示用户优先补以下字段中的任意 1 到 3 个：企业名称、统一社会信用代码/注册号、企业状态、成立日期、上市日期、员工人数、国家或地区、城市、地址、法定代表人、官网域名、企业邮箱、联系电话、分公司名称。
- 当需要直接面向客户展示时，优先复用以下引导文案：

`首屏标题`
请补充企业信息，帮助我确认是不是正确合作主体

`首屏说明`
提供任意几项信息即可开始核验。信息越完整，越容易排除重名、分公司和查错主体。

`输入框占位文案`
请输入企业名称、统一社会信用代码、地址、法定代表人、官网、电话等任意信息

`输入框下方辅助说明`
建议优先填写企业名称，或再补 1 到 2 项信息，例如成立日期、城市、地址、企业状态。

`信息不足时的轻提示`
当前信息较少，先补充企业名称、统一社会信用代码、地址、法定代表人中的任意一项，我可以更快帮你确认主体。

`继续比对提示`
如需进一步排除重名主体，建议继续补充成立日期、城市、地址、官网域名或企业状态。

`分公司场景提示`
如果你拿到的是分公司、支行、营业部或门店名称，也可以直接输入，我会先帮你核对总公司关系。

`示例问题`
- 这家公司是不是我要找的签约主体？
- 这个简称对应的是哪家正式公司？
- 这家分公司和总公司是什么关系？
- 旧名称和现在的主体是不是同一家公司？

- 如果用户完全不知道填什么，就给一个可直接复制、适合前端弹层或空状态的模板：

```text
你可以补充以下任意几项信息，我来帮你确认是不是正确合作主体：
- 企业名称：
- 统一社会信用代码/注册号：
- 企业状态：
- 成立日期：
- 上市日期：
- 员工人数：
- 国家或地区：
- 城市：
- 地址：
- 法定代表人：
- 官网/域名：
- 企业邮箱/电话：
- 分公司或总公司线索：
```

- 如果前端支持快捷标签，优先推荐这些标签：
`企业名称` `统一社会信用代码` `企业状态` `成立日期` `城市` `地址` `法定代表人` `官网/域名`
- 用户只补了弱线索时，先执行基础消歧，再明确说明还差哪个强标识。

### 1. Normalize The Clues

- 先提取用户已经给出的强线索：统一社会信用代码、注册号、完整工商名称、分支全称。
- 再提取中等线索：法定代表人、注册地址、联系电话、邮箱、官网域名、园区/开发区、集团归属、企业状态、成立日期、上市日期、国家或地区、城市。
- 把简称、品牌名、旧名称、旧地址、旧联系人视为弱或历史线索，除非后续有官方记录桥接。
- 员工人数可作为辅助识别线索，但默认不是强核验字段；若公开可核验信息不足，就把它列为“待用户补充比对”而不是硬判一致或不一致。
- 如果用户目标本质上是“确认能否签约”，优先确认“应签主体是谁”，而不是直接做风险深挖。

### 2. Route By The Strongest Available Clue

- 有统一社会信用代码或注册号时：先解析主体，再核对工商照面和三码。
- 输入明显是分公司、营业部、支行、门店时：先反查总公司，再确认用户到底要签哪一级主体。
- 只有完整企业名称时：先解析主体，再用工商照面核基础，再按已有线索补一个辅助核验点。
- 只有简称、品牌名、曾用名时：先拿候选集合，再用历史名称、变更记录和必要的聚合尽调缩小范围。
- 只有电话时：先做同电话企业反查，但只把它当成候选扩展，不当成最终证据。
- 地址与当前工商不一致时：优先检查地址变更和迁移记录，区分“同一家公司迁址”与“不是同一家公司”。
- 有官网、备案域名、企业邮箱线索时：优先用域名和年报网址做辅助比对。
- 有园区、开发区线索时：只把它作为场景佐证，不要用园区信息单独确认主体。

### 3. Build A Candidate Set

- 用 `qxb_op_enterprise_resolve` 获取候选时，不要猜正式全称。
- 候选很多时，先保留最 plausible 的 3 到 5 家，不要把长名单直接倒给用户。
- 对每一个候选统一比对：正式名称、统一社会信用代码、经营状态、成立日期、法定代表人、注册地址。
- 优先用强冲突排除候选；不要因为行业相近、品牌相近、同城就默认是同一家公司。
- 如果最终仍不能唯一确认，面对用户时只展示 2 到 3 个最相关候选，并说明每个候选为什么被保留。
- 每个保留候选至少写清：`企业名称`、`为什么像`、`哪里冲突`、`还差什么线索可以排除`。

### 4. Infer The Likely Contracting Entity

- 如果还不能“确认匹配”，但已经出现一个明显领先候选，就明确写“根据当前线索推测更可能的签约主体”为谁。
- 这个“推测主体”必须基于领先证据，而不是凭名称相似度拍脑袋。
- 推测主体常见形成条件包括：唯一领先候选、历史名称可桥接到当前主体、分支归属关系清晰但用户口径仍混用、名称和地址组合明显领先于其他候选。
- 如果没有明显领先候选，就不要硬推；直接写“当前不足以推测唯一签约主体”。

### 5. Check For A Better Contracting Entity

- 当当前匹配主体是分公司、支行、营业部、门店时，额外判断是否存在更合适的签约主体，例如总公司或母公司。
- 如果用户提供的主体能履约，但从合同抬头、开票、收款、授权链条看，总公司更合适，要单列“更合适的签约主体建议”。
- 不要默认总公司一定更合适；只有在分支权限、收款主体、合同目的或用户目标明显偏向总公司时才提出。
- 如果没有更合适的主体，就明确写“当前未发现更合适的签约主体”。

### 6. Check Name Or Brand Confusion Risk

- 对简称、品牌名、产品名、集团简称与法人主体不一致的情况，补一层“名称/品牌混淆风险”判断。
- 只在有依据时提示风险，例如：名称高度近似但统一社会信用代码不同、品牌词被不同主体同时使用、官网/域名与候选主体不匹配、地址或法定代表人冲突无法解释。
- 风险结论只用审慎表述，例如“无明显混淆风险”“存在一定混淆风险”“存在较高混淆风险”“疑似仿冒待进一步核验”。
- 不要把营销表述、非官方页面或单一弱线索直接写成“山寨公司”定性。

### 7. Verify With An Evidence Ladder

- 优先看统一社会信用代码、注册号、分支归属这类强证据。
- 强证据不足时，再组合两个彼此独立的中等证据，例如“法定代表人 + 注册地址”或“历史名称 + 名称变更记录”。
- 历史线索命中时，不要直接说“不匹配”；先确认是否存在曾用名、迁址、联系方式变更等桥接记录。
- 电话、邮箱、域名、园区、开发区只做辅助加分，不能单独决定结论。
- 需要更细的证据等级和冲突裁决规则时，读 [references/evidence-rules.md](./references/evidence-rules.md)。

### 8. Handle The Common Failure Modes

- 重名主体：比较统一社会信用代码、注册地址、法定代表人、成立日期，而不是只比较名称。
- 分支误当总公司：先查分支所属总公司，再明确用户是要签分支还是要签母体。
- 曾用名误判：先查历史名称，再用名称变更记录解释“旧名如何变成现名”。
- 旧地址误判：先查地址变更或迁移，确认是同一主体搬迁，还是线索落到了别的主体。
- 品牌名误当法人主体：把品牌、产品线、集团简称和实际签约主体拆开写清楚。
- 合同简称与发票抬头不一致：优先以统一社会信用代码和正式工商名称校准，再说明差异来源。
- 大品牌近似名称：如果出现“看起来像正牌，但公开工商或官网线索对不上”的情况，单列名称/品牌混淆风险，不要藏在备注里。

### 9. Escalate Only When Necessary

- 基础核验已足够时，直接输出主体核验结论，不要自动升级为深度尽调。
- 只有在下列情况下才扩大取证：
- 存在多个高相似候选主体。
- 需要同时看历史沿革、集团归属、网站域名、分支信息来拼出完整身份链。
- 用户明确要求“顺便看看这家公司整体情况”。
- 扩大取证时，优先走聚合尽调，再按需钻取局部区块，而不是无差别堆接口。

### 10. Ask For One Better Clue When Still Ambiguous

- 无法确认时，只问一个最高信号的问题，不要一次抛给用户一长串补件清单。
- 默认按以下顺序补线索：统一社会信用代码或注册号、完整注册地址、法定代表人、官网域名/企业邮箱、分公司全称。
- 问题要直接服务于消歧，例如“请补一下统一社会信用代码，或补一个完整注册地址，我可以立刻排除重名主体。”

### 11. Build A Comparison Table Before Closing

- 在形成最终回答前，先把用户已填线索和核验结果整理成对照表，再给结论。
- 对照表默认使用以下列：
- `核验维度`
- `用户填报信息`
- `核验结果`
- `核验来源`
- `是否一致`
- `备注`
- `核验来源` 只用业务可读标签，例如“工商照面”“三码”“历史名称”“变更记录”“分支所属总公司核查”“联系方式”“域名信息”“年报网址”“迁移情况”“园区/开发区归属”“客户信息尽调”。
- `是否一致` 只用四档：
- `一致`
- `部分一致`
- `不一致`
- `未核验`
- 用户没有提供的维度默认不强行补满；只有当这些维度能帮助下一步消歧时，才把它们列入表格并标记为 `未核验`。
- 优先展示这些维度中的已填项和高价值项：企业名称、统一社会信用代码/注册号、企业状态、成立日期、上市日期、国家或地区、城市、地址、法定代表人、官网域名、企业邮箱、联系电话、分公司/总公司关系。
- 如果存在多个候选、明显名称混淆，或用户给出的依据与当前核验结果存在冲突，再追加一个候选对比表。
- 候选对比表默认使用以下列：
- `候选企业`
- `保留原因`
- `主要冲突点`
- `混淆风险`
- `建议补充线索`
- 候选对比表最多保留 3 行，不要把搜索结果长名单直接展示给用户。
- 如果当前已经确认唯一主体，且不存在高相关混淆主体，可以不输出候选对比表。

## Output Contract

默认按固定结构输出，避免写成长篇散文：
1. `核验结论`
2. `根据当前线索推测的签约主体`
3. `更合适的签约主体建议`
4. `名称/品牌混淆风险`
5. `主体核验对照表`
6. `其他可能主体或候选项对比（如适用）`
7. `关键冲突点与未核验项`
8. `下一步建议`

结论标签只用以下四档，不要自由发挥措辞：

- `确认匹配`
- `基本匹配，但签约前需补一个强标识`
- `不匹配`
- `存在多个候选，暂不能确认`

输出约束：
- 一旦能确认主体，就明确写出正式全称，不要只写简称。
- 一旦能拿到统一社会信用代码，就显式展示。
- `根据当前线索推测的签约主体` 允许为空，但如果存在明显领先候选，就必须写。
- `更合适的签约主体建议` 必须明确写“未发现”或写出推荐主体及原因，不要留白。
- `名称/品牌混淆风险` 必须明确写风险等级和一句依据，不要只在备注里一笔带过。
- `主体核验对照表` 优先用 Markdown 表格输出。
- `其他可能主体或候选项对比` 在存在多个高相关候选、名称混淆或关键冲突时必须输出；否则可省略。
- `关键冲突点与未核验项` 需要把“用户当前依据”和“公开核验结果”之间最关键的不一致点单列出来，例如名称近似但统一社会信用代码不同、地址不符、法定代表人不符、分支与总公司口径混用。
- 表格里同时放“用户填报信息”和“核验结果”，方便业务、法务、采购直接肉眼比对。
- 表格里的“核验来源”只写业务标签，不写技术接口编号。
- 若发现“用户想签总公司，但当前线索落在分公司”，要把这个差异写成主结论，而不是藏在备注里。
- 若仍有多个候选，给一个紧凑对比，并在“其他可能主体或候选项对比”里只保留 2 到 3 个最相关候选。
- 不要把“未查到”写成“没有”；信息不足时明确写“当前公开可核验信息不足以确认”。
- 若用户给出的字段很少，`下一步建议` 要明确建议补充哪些字段继续比对，例如“请继续补企业状态、成立日期、城市或地址中的任意两项，我可以进一步缩小候选主体”。

## Escalation And Stop Conditions

- 主体已确认，且用户要继续看整体画像、合作前风险、资质和集团情况时，可转入 `$qixin-cn-enterprise-detail-report`。
- 当前线索不足以区分候选主体时，先停在“补充一个更强线索”，不要硬做结论。
- 若识别结果不是中国企业主体，或当前问题超出国内企业能力边界，要明确说明边界并停止当前流程。
