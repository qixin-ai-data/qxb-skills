# Qixin Enterprise Batch Search

## Overview

这是一个面向地图搜索和园区企业搜索的 skill。它不假设 MCP 已经提供“全国范围任意多条件一次搜企业”的总入口，而是先选择当前可用的批量列表接口拿到候选企业，再按需做二次筛选与结构化输出。

核心目标是尽快产出“企业名称 + EID + 核心标识字段”的可用名单，便于继续做尽调、监控、关系分析或导出。

## Working Principles

- 只处理国内企业主体，不走海外主体流程。
- 先做能力预检，再决定是否继续，不编造不存在的批量检索能力。
- 优先使用当前 MCP 已支持的批量列表接口，不先拉大批量企业后盲目本地过滤。
- 输出聚焦企业名单与关键标识字段，不把内部调用细节暴露给用户。
- 只做查询、筛选、整理和导出建议，不调用任何监控写入、订阅或名单管理工具。
- 先产出标准化中间结果，再生成面向用户的话术，降低不同模型在分析思路、篇幅和措辞上的漂移。
- 默认面向“企业主体”名单，不把分公司、营业部、分支机构和历史迁移主体直接混入主名单，除非用户明确要求。

## Capability Check

开始任务前，先用 `qxb_op_api_spec_get` 校验本次会用到的接口，至少覆盖：

- 一个批量列表入口接口
- 一个用于补齐 EID 的企业基础接口
- 用户明确要求的二次筛选接口

若当前请求没有对应的批量入口，就直接说明阻塞点。不要把“当前不支持的全国多条件企业检索”伪装成可执行流程。

## Supported Batch Entry Routes

### Deterministic Route Selection

先做关键词级硬匹配，再决定入口，不允许自由发挥：

- 用户输入含 `开发区`、`经济技术开发区`、`高新技术产业开发区`、`经开区`：
  - 必须优先走 `开发区企业路线`
- 用户输入含 `园区`、`产业园`、`科技园`、`保税区`：
  - 必须优先走 `园区企业路线`
- 用户输入含 `周边`、`附近`、`X 公里`、`3 公里`、`5 公里`，或明确给出锚点企业：
  - 必须优先走 `周边企业路线`

若同时出现多个信号，按以下优先级：

1. 明确半径或“周边/附近”语义
2. 明确开发区语义
3. 明确园区语义

对于 `哈尔滨经济技术开发区` 这类输入，不得先尝试园区接口；应直接使用开发区接口。

### 1. 周边企业路线

当用户提供以下任一信息时，优先走周边检索：

- 锚点企业名称或统一社会信用代码
- 明确坐标
- 明确“某地周边 X 公里”的范围检索需求

优先接口：

- `cn_nearby_company_search`：已知锚点企业，查其周边企业
- `cn_nearby_company_count`：先估算总量
- `cn_nearby_company_detail`：按坐标和半径取企业列表

这一路线最适合：

- 附近供应商/竞品搜寻
- 某工厂、园区、商圈周边企业筛选
- 需要行业、注册资本、经营状态初筛的地理型检索

### 2. 园区企业路线

当用户给出明确园区名称时，优先走：

- `cn_industrial_park_companies`

该路线适合：

- 指定产业园、科技园、保税区内企业名单
- 园区内按成立时间、状态做初筛

### 3. 开发区企业路线

当用户给出明确开发区名称时，优先走：

- `cn_development_zone_companies`

该路线适合：

- 国家级/省级开发区企业名单
- 先拿区内企业，再做二次标签或主体性质筛选

## What Is Not Natively Supported

当前 MCP 目录里，没有一个可直接支持以下需求的“通用全国企业搜索总接口”：

- 仅凭“省市 + 行业 + 规模 + 企业类型”直接全国批量搜企业
- 仅凭“北京市高新技术企业”直接一次返回全量企业名单
- 仅凭“浙江省纺织中型企业”直接一次返回结构化企业列表

遇到这类请求时，先明确说明限制，再把请求改写成当前可执行的入口之一：

- 指定园区或开发区
- 指定锚点企业做周边检索
- 提供更窄的地理载体或候选名单

必要时提示用户补充“园区名 / 开发区名 / 锚点企业 / 坐标半径”中的一种。

## Condition Parsing

把用户自然语言拆成两类条件：

### A. 可直接下推到批量列表接口的条件

- 园区名称
- 开发区名称
- 锚点企业
- 经纬度与半径
- 经营状态
- 成立时间范围
- 注册资本区间
- 行业代码或明确行业过滤

### B. 需要候选名单拿到后再做二次筛选的条件

- 高新技术企业、专精特新、上市、互联网、外贸等标签类条件
- 小微企业、规上企业
- 大型/中型/小型/微型
- 民营、央企、地方国企、事业单位、个体工商户等主体性质
- 经营范围关键词
- 地址关键词

如条件含义模糊，优先做保守解释并在输出中写明本次采用的筛选口径。

## Two-Stage Workflow

### 第一步：选择批量入口并拉取候选企业

- 先按 `Deterministic Route Selection` 做硬匹配，再判断用户请求能否落到“周边 / 园区 / 开发区”三类入口之一。
- 默认返回前 100 条；若接口总量明显更大，先告知总数，再说明当前只展示前 100 条。
- 分页接口按 `skip=0` 开始；确有必要时继续翻页。
- 对候选企业做基础去重，优先使用统一社会信用代码，其次使用企业名称。

若首选路线命中失败，只允许按以下顺序降级：

1. 校验是否为名称不精确导致的 exact name miss
2. 尝试同类入口的近似名称修正
3. 仍失败时再提示用户补充更精确地理载体

不要把 `开发区` 请求静默降级成 `园区` 或 `周边` 请求。

### 第二步：按需做二次 enrich 与筛选

对最终要保留的企业，优先用 `cn_company_registration_face` 补齐：

- EID
- 标准企业名称
- 统一社会信用代码
- 法定代表人
- 注册资本
- 成立日期
- 经营状态
- 注册地址
- 经营范围

若用户还要求其他维度，再按需补充：

- `cn_company_concept_labels`：高新、专精特新、互联网、外贸、上市等标签
- `cn_company_scale`：大型/中型/小型/微型
- `cn_company_entity_nature`：央企、国企、民营、事业单位、个体等主体性质
- `cn_company_capital_background`：资本背景
- `cn_company_sme`：小微企业识别
- `cn_company_above_scale`：规上企业识别
- `cn_company_industry_nec`：国民经济行业分类

### 第三步：做一致性与剔除检查

在输出前，对候选企业统一做以下检查：

- 地理一致性检查
- 主体层级检查
- 资本口径检查

#### 地理一致性检查

如果批量入口来自开发区、园区或周边范围，优先用工商照面的当前注册地址做复核：

- 当前注册地址与入口范围明显一致：保留
- 当前注册地址明显不在入口范围内，但列表接口命中过：默认降为 `待人工确认`
- 当前注册地址明显迁移到外地，且用户要的是“当前可跟进名单”：默认剔除

例如：

- 开发区企业列表命中，但工商照面地址已经迁到外省
- 历史名称或历史关联命中当前入口，但现主体已不在该区域

除非用户明确要“历史入园企业”或“曾在本地注册过的企业”，否则按当前主体地址优先。

#### 主体层级检查

默认优先保留独立企业主体，以下类型默认降级或剔除：

- 分公司
- 分支机构
- 营业部
- 电话局、服务部、经营部等明显分支口径

处理规则：

- 用户明确要“分公司/营业网点/分支布局”时：保留
- 用户要“客户名单/供应商名单/可跟进企业主体”时：默认剔除

可依据以下信号判断：

- 企业名称含 `分公司`、`分支机构`、`营业部`、`服务部`
- 工商照面显示为分支主体

#### 资本口径检查

注册资本比较默认按人民币口径理解。若遇到外币资本：

- `currency_unit = CNY`：可直接按数值比较
- 非 `CNY`：默认不直接判定“命中注册资本条件”
- 非 `CNY` 且没有可靠换算口径：写入 `核验备注 = 资本口径待人工确认`

不要因为数值恰好小于 500 就把 `500 万美元` 当作 `500 万人民币` 处理。

### 第四步：处理工具异常

若 MCP 出现临时错误、解码异常、超时或部分接口不可读：

- 先重试一次同一接口
- 若仍失败，只保留已经完成核验的字段
- 不把接口失败写成“企业不符合条件”
- 在输出中用业务化表述写 `部分字段暂未核验`

不要因为二次筛选接口失败而把企业直接降为负样本。

## Reproducible Execution Contract

为提升跨模型复现性，严格按以下顺序执行，不跳步，不合并：

1. 把用户条件转换成标准化条件对象
2. 选择唯一的批量入口路线
3. 拉取候选企业并做去重
4. 生成逐家企业的标准化核验对象
5. 按固定规则计算匹配等级
6. 按固定排序输出
7. 最后才生成面向用户的自然语言总结

不要先写总结再回填证据，也不要边查边写长段分析。

### Standardized Query Object

先在内部整理出如下结构，不对用户原样展示：

```json
{
  "entry_route": "nearby|park|zone",
  "location_anchor": "",
  "industry_keywords": [],
  "status_required": [],
  "registered_capital_min": null,
  "registered_capital_max": null,
  "start_date_range": null,
  "tag_filters": [],
  "entity_nature_filters": [],
  "scale_filters": [],
  "scope_keywords": [],
  "page_size": 100
}
```

若某条件无法直接映射，也要放进对象里并标记为“待二次核验”，不要在后续步骤里临时改口径。

### Standardized Company Record

对每个候选企业，内部统一整理为如下结构：

```json
{
  "name": "",
  "eid": "",
  "credit_no": "",
  "oper_name": "",
  "registered_capital_text": "",
  "registered_capital_value_wan": null,
  "currency": "",
  "start_date": "",
  "status": "",
  "address": "",
  "industry": "",
  "tags": [],
  "entity_nature": "",
  "scale": "",
  "scope": "",
  "entry_location_consistent": null,
  "is_branch_like": null,
  "match_flags": {
    "entry_route_match": false,
    "status_match": false,
    "capital_match": false,
    "industry_match": false,
    "tag_match": false,
    "entity_nature_match": false,
    "scale_match": false,
    "scope_match": false
  },
  "verification_notes": []
}
```

没有核验到的字段保留为空或写入 `verification_notes`，不要用模型猜测补齐。

### Fixed Match Logic

企业筛选结论只允许使用三档：

- `强匹配`
- `部分匹配`
- `待人工确认`

判定规则固定如下：

- `强匹配`：入口条件命中，且经营状态、注册资本、核心行业或标签条件均命中，且无关键字段缺失
- `部分匹配`：入口条件命中，但只有部分业务条件命中，或存在 1-2 个未核验字段，或主体层级需要人工确认
- `待人工确认`：入口条件命中，但关键字段缺失、标签未核验、行业判断只能靠经营范围关键词近似推断，或地理一致性/资本口径存在疑点

不要输出“高度匹配”“非常合适”“可能符合”“疑似优质”这类自由表述，统一使用上述三档。

### Fixed Sorting Rules

最终企业列表必须按以下顺序排序：

1. 匹配等级：`强匹配` > `部分匹配` > `待人工确认`
2. 经营状态：存续/在业优先于其他状态
3. 注册资本：更接近用户设定区间中值者优先；若未给区间，则按注册资本从高到低
4. 成立日期：较新的优先
5. 企业名称：按中文名称字典序作为最后的稳定 tie-breaker

不要根据模型主观判断临时调整排序。

## Filtering Strategy

- 对于列表接口已经支持的条件，优先在接口层过滤。
- 对于标签、主体性质、规模等条件，只在候选集足够小的时候做逐家补充筛选。
- 如果候选集过大，不要盲目逐家补接口；先返回统计概览和前 N 条，并建议缩小条件。
- 某个二次筛选接口返回空值时，不要默认判定“不符合条件”；应标记为“未核验”或提示结果有限。
- 对于开发区/园区/周边列表命中的企业，若当前注册地址已明显迁出目标区域，默认不进入最终主名单。
- 对于非人民币注册资本，除非有可靠换算口径，否则不要直接参与资本阈值比较。
- 对于分公司、营业部、服务部等分支主体，默认不进入“企业主体名单”。

## Output Contract

默认输出四部分，且顺序、字段名、粒度保持固定：

### 1. 检索条件

- 明确列出本次实际采用的入口路线
- 明确列出已执行的筛选条件
- 明确列出未能直接执行、仅做近似处理或未核验的条件
- 本节不超过 6 行

### 2. 结果概览

- 符合当前入口条件的企业总数
- 本次实际返回条数
- 已完成二次核验的条数
- 结果是否仅为前 N 条
- 本节只写事实，不写扩展分析

### 3. 企业列表

至少输出以下字段：

- 序号
- 企业名称
- EID
- 统一社会信用代码
- 法定代表人
- 注册资本
- 成立日期
- 经营状态
- 注册地址
- 匹配说明
- 匹配等级
- 核验备注

`匹配说明` 句式固定为：

- `命中入口条件；命中经营状态；命中注册资本；命中行业/标签条件`
- 若某项未核验，写 `行业条件待核验`、`标签条件待核验`
- 若主体疑似分支，写 `主体层级待确认`
- 若地址与入口范围不一致，写 `地理一致性待确认`
- 若资本为外币，写 `资本口径待确认`

不要在表格里写长段解释。

### 4. 后续建议

- 若用户需要逐家深挖企业详情，可转到 `$qixin-cn-enterprise-detail-report`
- 若用户需要继续看企业关系网络，可转到 `$qixin-enterprise-relationship-report`
- 若用户需要看关键人员或董监高，可转到 `$qixin-executive-person-report`
- 若用户需要长期跟踪，只建议导出 EID 列表，不直接调用监控写入工具
- 本节最多给 3 条建议，且必须直接对应当前结果

## Writing Style Constraints

为减少不同模型的文风漂移，生成用户可见内容时遵守以下限制：

- 不写长段行业评论，不做超出证据的数据解读
- 优先写短句，不写修辞性总结
- 不使用“优质”“值得重点关注”“成长性强”“建议优先接触”之类主观措辞，除非用户明确要求主观推荐
- 只基于当前核验字段说话，不把“未查到”表述成“没有”
- 每次结果概览最多 4 个要点
- 每次后续建议最多 3 个要点
- 对于工具异常，只写“部分字段暂未核验”，不写技术报错

如果需要更强复现性，额外读取 [references/reproducibility-rules.md](./references/reproducibility-rules.md) 并严格执行其中的固定句式和输出模板。

## Export Guidance

- 默认直接在回复中给表格或 JSON 片段。
- 用户明确要求文件时，优先生成 CSV 或 JSON。
- Excel 不是当前 skill 的默认交付能力；只有在当前环境存在可靠写出工具时才生成，否则回退到 CSV。

## Edge Cases

### 结果过多

- 超过 1000 条时，先给总量、前 100 条和收窄建议。
- 优先建议用户补充园区、开发区、锚点企业、半径、状态或注册资本区间。

### 结果过少

- 少于 10 条时，直接返回全部结果。
- 视情况建议放宽半径、放宽状态、取消标签类二次筛选。

### 无结果

- 明确说明当前入口下未检索到符合条件的企业。
- 建议放宽半径、调整园区/开发区范围，或去掉某些二次筛选条件。

### 条件无法直接执行

- 明确指出“当前 MCP 没有对应的通用批量接口”。
- 提供可执行替代方案，而不是停留在抽象说明。

## Internal Tooling Rules

- 国内企业主体解析优先使用 `qxb_op_enterprise_resolve`，不直接猜企业全称。
- 首次调用任何接口前，先用 `qxb_op_api_spec_get` 看参数说明。
- `api_ref` 必须使用目录中的原始 route ref，不自行改写。
- 只用查询接口，不调用 `qxb_op_monitor_manage`、监控面板或其他写操作工具。
