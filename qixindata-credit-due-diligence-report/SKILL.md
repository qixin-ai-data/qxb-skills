# Qixin CN Credit Due Diligence Report

## Overview

围绕单一中国企业主体，生成可直接用于授信初审、授信评审、审批会签和贷前资料整理的正式授信尽调底稿。默认先建立“主体识别 -> 控制链 -> 经营资质 -> 财务/信用 -> 风险暴露 -> 授信建议”的统一事实底座，再生成 Markdown 工作稿并优先导出 PDF 正式报告。

## Credit Positioning

- 把本 skill 视为“授信尽调基础材料生成器”，不要把它写成最终授信批复、法律意见、审计报告或监管结论。
- 优先解决“公开信息分散、风险项分散、关系链信息分散”的拼接问题，帮助授信经理和审批人员快速形成首版底稿。
- 围绕以下授信问题输出：`这是谁`、`谁控制`、`是否持续经营`、`公开风险在哪里`、`财务是否可验证`、`还缺什么材料`、`下一步建议是什么`。

## Safety Boundaries

- 只执行只读查询、分析和报告生成；不要执行监控、名单维护、写回、订阅或外发动作。
- 不要把授信建议写成“批准/拒绝授信额度”；统一写成 `建议进入评审`、`补充材料后进入评审`、`建议进一步专项核查`、`当前不建议推进`。
- 不要暴露 `api_ref`、`api_id`、`MCP`、`result_ref`、`JSONPath` 或底层调用细节。
- 不要把“当前未查到”写成“没有”；信息不足时统一写“基于当前可核验的公开信息，相关资料暂不充分”。
- 不要臆测财务、税务、许可、评级、司法或处罚结果；没有命中时只写公开信息边界。
- 不要把营业执照原件、身份证号、银行账号、印章图片、合同扫描件等敏感材料写入 skill 资源或示例。
- 仅在确有公开披露数据时写入财务三表和财务指标；财务接口主要适用于上市企业或有公开披露财务数据的主体，未命中时必须降级为“财务公开数据有限”。

## Working Style

- 先确认主体，再汇总事实，再出结论；不要边查边写最终判断。
- 先用细粒度接口搭底，再用聚合接口兜底；不要默认把所有聚合结果整段搬进报告。
- 第一次调用某个新接口前，先做 `qxb_op_api_spec_get`；不要猜参数名。
- 从企业名称、统一社会信用代码或注册号出发时，先做 `qxb_op_enterprise_resolve`；不要直接假定主体唯一。
- 优先使用正式企业全称、统一社会信用代码或注册号传参；不要默认用 `eid`。
- 把报告写成“授信审查底稿”，而不是“企业百科”或“营销式画像”。

## Internal Case Object

先把线索整理成内部对象，再决定下钻路径和报告重点：

```json
{
  "provided_name": "",
  "canonical_name": "",
  "credit_code": "",
  "reg_no": "",
  "credit_scenario": "new-credit|renewal|supplier-credit|dealer-credit|generic",
  "report_scope": "standard|risk-heavy|relationship-heavy|financial-heavy|supply-chain-heavy",
  "existing_materials": [],
  "core_questions": [],
  "focus_risks": [],
  "business_background": ""
}
```

不要把这个对象原样展示给用户；它只用于固定授信底稿的推理顺序和章节取舍。

## Workflow

### 1. Normalize The Request And The Report Scope

- 识别当前场景是新增授信、续作复核、供应链授信、经销商授信、担保方尽调还是泛化底稿整理。
- 识别用户更关心哪一类问题：标准底稿、风险优先、关系链优先、财务优先或供应链优先。
- 识别用户是否已经提供营业执照、统一社会信用代码、历史名称、官网、主要股东、授信背景等补充线索。
- 若用户只说“帮我做 A 企业授信尽调底稿”，默认按 `standard` 范围执行，不要反复追问。
- 若用户只给出企业简称或旧名称，先记录为弱线索，后续用历史名称和变更记录桥接。

### 2. Resolve The Enterprise And Lock The Subject

- 先用 `qxb_op_enterprise_resolve` 确认中国企业主体，再用工商照面、三码和联系方式做交叉确认。
- 优先锁定以下强标识组合之一：
  - `统一社会信用代码`
  - `注册号`
  - `正式企业全称 + 法定代表人`
  - `正式企业全称 + 注册地址`
- 若命中分支机构名称，先用分支总公司核查判断授信对象到底是分支还是总公司，再决定后续报告主体。
- 若线索来自旧名称、旧地址或旧官网，用历史名称、变更记录、迁移记录和域名备案判断是否为同一主体。
- 若主体无法唯一确认，只问用户一个更强线索；不要在主体歧义状态下继续生成正式授信结论。

### 3. Build The Credit Subject Foundation

- 先拉基础工商信息，再补经营支撑线索，优先覆盖：
  - 工商照面与基础工商报告
  - 三码信息
  - 联系方式、域名、年报网址
  - 行业、规模、主体性质、资本背景
  - 企业简介、主营业务
- 明确写清以下内容：
  - 企业全称
  - 统一社会信用代码 / 注册号
  - 法定代表人
  - 成立日期
  - 注册资本
  - 经营状态
  - 注册地址
  - 主营方向
- 若经营状态显示注销、吊销、撤销、清算或其他明显异常，直接把它升级为授信关注重点。

### 4. Build Ownership, Control Chain And Group Layout

- 先查工商股东和主要人员，再补实际控制人、实际受益人、同实控企业、集团成员和分支机构。
- 说明股权集中度、资本背景、控制链清晰度和集团化程度，不要只堆名单。
- 若股东、实际控制人、实际受益人口径冲突，保守写成“控制链公开资料存在口径差异，建议进一步专项核查”，不要强行下唯一结论。
- 若企业存在较大集团、较多分支或多层控制结构，在报告中单列“集团与关联布局”而不是藏在备注里。

### 5. Build Qualification, Tax And Operating Support Blocks

- 默认覆盖以下经营支撑项：
  - 资质证书
  - 行政许可
  - 纳税 A 级记录
  - 纳税人类型
  - 社保披露
  - 域名与网站备案
- 若主体属于金融、支付、电信、工程等牌照敏感行业，按需追加金融资质、电信许可或工程资质接口。
- 不要把未命中资质直接写成“没有资质”；统一写成“当前公开可核信息未见相关资质或许可，建议结合用户内部资料复核”。

### 6. Build Financial And Credit Observation

- 默认补充以下授信辅助指标：
  - 启信分
  - 综合风险分
  - 合同违约指数
  - 空壳指数
  - 主体信用评级
- 若主体存在公开披露的财务数据，再追加：
  - 财务主要指标
  - 资产负债表
  - 利润表
  - 现金流量表
- 财务三表和财务指标优先用于上市企业或存在公开披露财务数据的主体；若未命中，不要据此推断“财务差”或“无经营”。
- 当财务公开数据有限时，用纳税记录、社保披露、企业规模、主营业务、供应链线索和经营状态作为替代观察信号，并显式说明边界。

### 7. Build The Risk Scan

- 默认先做风险总览，再按命中模块深挖，不要把所有风险接口一次性全打。
- 风险总览优先覆盖：
  - 经营异常
  - 严重违法
  - 司法风险评分
  - 风险统计
  - 行政处罚
  - 税务风险
  - 股权和资产负担
- 命中重点风险后，再选择性补查：
  - 被执行
  - 失信被执行
  - 限制高消费
  - 欠税信息
  - 非正常户
  - 重大税收违法
  - 动产抵押
  - 股权出质
  - 股权冻结
  - 司法协助
  - 终本案件
  - 破产案件
- 把风险事项写成“事项类型 + 时间/阶段 + 核心影响”，不要把原始字段整段贴入报告。

### 8. Build External Operation And Supply Chain Signals

- 当授信场景关注真实经营、交易背景或上下游稳定性时，补充企业客户、企业供应商、供应链上下游和对外投资信息。
- 把这类数据写成“外部经营线索”而不是“已证实交易事实”；它们适合辅助判断经营活跃度和合作网络，不直接等同于合同履约证明。
- 若相关数据有限，明确写“公开经营协同线索有限”，不要夸大判断。
- 若用户未明确要求深挖上下游，但外部经营线索已出现较强样本，补一句自然语言确认：`是否需要继续深挖上下游、核心客户/供应商或交易背景线索`；若用户未回复且当前目标只是标准授信底稿，则保持轻量线索口径，不默认无限扩展。

### 9. Use Aggregate APIs Only To Fill Gaps

- 需要一次性补齐多块基础信息时，使用 `cn_customer_due_diligence`。
- 需要一次性排查多块风险时，使用 `cn_cooperation_risk_scan`。
- 对聚合接口先看 preview，再按 [references/mcp-playbook.md](./references/mcp-playbook.md) 中的 JSONPath 定点下钻。
- 不要让聚合结果覆盖已经用细粒度接口确认过的核心事实。

### 10. Apply Sanity Checks And Rate The Case

- 在写报告前统一整理事实表，至少核对企业名称、统一社会信用代码、经营状态、法定代表人、注册地址和控制链口径是否一致。
- 固定按 [references/analysis-rubric.md](./references/analysis-rubric.md) 的维度给出结论，不要临时更换评价框架。
- 至少显式写出 `1` 到 `3` 个最关键的授信关注点或阻断点，不要只给笼统风险结论。
- 若信息不足以支撑强结论，把不确定性写清楚，并同步生成待补材料清单。

### 11. Draft The Markdown Working File

- 严格按 [references/report-template.md](./references/report-template.md) 生成 Markdown 工作稿。
- 默认文件命名为：`[企业简称]_授信尽调底稿_[YYYY-MM-DD].md`
- 默认先表格、后短分析；不要写成长篇散文。
- 把风险摘要、待补材料、建议动作和综合授信建议显式写入报告，不要只留在对话说明里。
- 若用户提供了授信场景、产品类型、审批问题或业务背景，把它写入“授信背景/本次关注点”位置。

### 12. Export The Final PDF

- 用 [scripts/export-report-pdf.js](./scripts/export-report-pdf.js) 把 Markdown 导出为正式 PDF。
- 推荐顺序如下：
  1. 完成 Markdown 工作稿
  2. 执行 `node .\\scripts\\export-report-pdf.js "<report.md>" --logo "<logo.png>"`
  3. 确认同名 `.pdf` 文件已生成且文件大小大于 `0`
  4. 优先向用户交付 PDF 路径
- 若环境无法直接导出 PDF，可以保留同名 HTML 打印稿作为过渡件，但对外统一表述为“已生成可打印版本，可继续导出 PDF”。

## Output Contract

- 默认正式交付件：`[企业简称]_授信尽调底稿_[YYYY-MM-DD].pdf`
- Markdown 工作稿：`[企业简称]_授信尽调底稿_[YYYY-MM-DD].md`
- 可选 HTML 打印稿：`[企业简称]_授信尽调底稿_[YYYY-MM-DD].html`
- 报告正文默认覆盖：
  1. 执行摘要
  2. 授信对象与主体识别
  3. 股权结构、实际控制人与关联/集团
  4. 经营概况与资质许可
  5. 财务与偿债能力观察
  6. 风险排查
  7. 外部经营与供应链线索
  8. 评分与信用观察
  9. 综合判断、待补材料与建议动作
- 若个别维度公开信息不足，也要保留该章节，并明确写出“当前可核验公开信息有限”。

## Escalation And Stop Conditions

- 若主体无法唯一确认，先停在“补一个更强线索”，不要继续生成正式底稿。
- 若用户只要一个快速“能否继续准入/开户/入驻”的判断，而不是正式授信底稿，转用 `$qixin-cn-pre-admission-check`。
- 若用户想要更偏企业全景画像、客户可交付深度报告，而不是授信视角的底稿，转用 `$qixin-cn-enterprise-detail-report`。
- 若识别结果不是中国企业主体，或问题超出国内企业能力边界，明确说明边界并停止当前流程。
